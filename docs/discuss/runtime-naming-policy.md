`docs/plan/runtime-naming.md` で指摘された問題点に関して、私の考えを述べます。
（実装から大分時間が経ってしまっているため、実装とは乖離した意見になっている可能性があります）

## 前提

yatt はコード生成と名前空間の構築（とその dispatch）のための枠組みです。
テンプレートから生成されたコードが名前空間を作るだけでなく、
その名前空間にユーザーが定義した関数（entity関数）が取り込まれて利用されるケースもあります。

そのため、生成されるコードがどのような名前空間に置かれどのような命名規則に基づいて構造化されているのか、
ユーザーがその生成されたコードと相互作用する関数を書くときにはどのような
ルールに従う必要が有るのかが、明確にルールづけされるべきであることは疑いありません。

ですので、ここで改めて現在まで私が考えていた命名の方針を解説します。
この方針が LLM 的に納得できるものかどうか、議論していきましょう。

### `$` プレフィクスの位置づけ

`$` プレフィクスは第一義的には、その名前空間のメンバーが yatt によって
直接的に制御され、プロジェクトごとに内容が変動することを意味しています。
（衝突回避は、副次的な効果という考えです）

ESM の世界観に慣れ親しんだプログラマーは、`yatt` という名前を見たときに、
その中身が静的に（プロジェクトによらず）確定しているかのように期待してしまうかもしれない。
そのように期待させないために、`$yatt` としています。

`$` のついた名前空間（ `$yatt`, `$yatt.$public`, `$yatt.$staticMap` …）は、

- yatt によってメンバーを制御される名前空間である
- プロジェクトが異なれば、そのメンバー構成も変化する

#### `$yatt.runtime` について

（entity による上書きの問題については後で論じます）

`$yatt.runtime` は、そのメンバーが静的に確定している
（その中の名前はプロジェクトを超えて参照できる）ことを示すため、
`$` 抜きの名前を用いています。

ただし、 `$yatt.runtime` の実装はプラットフォームごとに変更する必要があると考えています。

### entity を置く名前空間について

ここは大いに迷っているところです。そもそも、entity を定義する typescript module の
置き場所すら、まだ迷っています。（旧 clasp 版の `root/_yatt.entity.ts` からリストアップする仕組みは、あくまで暫定的なもの）

名前空間については、理論上は、以下のような候補が考えられるでしょう。

- `$yatt.<entity名>`, `$yatt.$<entity名>`
- `$yatt.entity.<entity名>`, `$yatt.$entity.<entity名>`

実際の所、entity 関数の呼び出しは、次の３箇所に書かれる可能性があります。
1. yatt widget 内
2. yatt action 内
3. entity 定義内

このうち 1 については yatt がコード生成を行うため、関数への path が深くなったり
prefix がついても問題はありません。
しかし残る 2, 3 はプログラマーが自分で関数への path を記述するので、
プログラマーの負担は無視できません。勝手につく prefix は少ないほうが良いと考えました。
それが、`$yatt.<entity名>` を採用した理由です。


今後の populator 版においては、`public/_*entity.ts`, `entities/*.ts` を
`await import()` を用いてロードし、それを `$yatt` の直下のメンバーにする
（ただし、 runtime などの衝突する予約名前は拒否する）、
というアプローチが出来ないかと考えています。

### `public` という名前について

テンプレートを置くディレクトリを他のフレームワークでは `pages/` と呼ぶことが多いように
思いますが、
これは build によるコード生成を前提とした考え方です。

それに対して（clasp 対応ではやむなく build を行いますが）
本来の yatt は build を極力意識しなくて良いことを設計目標としています。

別の言い方をすれば、yatt では Apache や PHP のような古典的な web resource
解釈を再現したいと考えています。つまり、

- `public/` フォルダーに置いたものは、オンデマンドで（例えば拡張子による）必要な処理を
透過的に施された上で、サーブされるリソースとなる。
- 上記の処理をバイパスしたい、完全に static なものは、別途 `static/` フォルダーに置く

とはいえ、上記はあくまで一般の web app の場合のフォルダ構成です。

GAS clasp3 においては build が不可避であるため、従来どおり、 `pages/` → `root/` 
という構成でも構わないと考えています。

ただ、clasp 用に書いたアプリケーションを、entity だけ別の実装に差し替えて、
deno でローカルで画面デザインを試す道は、残しておきたいと考えています。

これについては明確な注意書きが必要となるでしょう。

### `typeof$yatt` について

typeof という prefix が誤解の元であるという指摘は理解できます。

これについては、他のポリシーと矛盾しない範囲で、より良い命名のアドバイスをもらいたいです。

いっそ `t$yatt` や `type$yatt` とかでも良いのかもしれません。

### `$this` について

これも迷っている要素の一つです。Perl 版 yatt においては、テンプレートの呼び出しは
クラスメソッド呼び出し形式を行う仕組みを採用しており、各テンプレートは `$this` を通して
現在のテンプレート（をトランスパイルして得られたクラス）にアクセスすることが出来ました。
これは動的 dispatch を実装するために非常に有益でした。

この経験があったため、テンプレートの実体を指す変数が必要だと考えました。
yatt-js においても、少なくとも widget の動的 dispatch は実装可能にしておきたいです。

その際に、JS において `this` に頼ることは危うい（分かりにくいバグのもとになる）かもしれない、という不安があり、現時点では独自の `$this` を用意する、という仕組みになっています。

### internTemplateRuntimeNamespace について

名前衝突は、私の意図しない、単なるバグの可能性があります。

現在の実装に拘らずに目的を記述するとすれば、以下のようになります：

- `public/` 以外にもテンプレートの置き場所を（複数？）持てるようにしたい（これは private な、外部からは直接アクセスできないテンプレートとなる）

  - 例えば `ytmpl/` フォルダーに置いたテンプレート `foo.yatt` の widget `bar` を
    ```ts
    $yatt.$ytmpl.$foo.render_bar(CON, {...});
    ```
    のように呼び出せるようにしたい。（`$foo` か `foo` かは、少し迷います）

### CON, BODY の all caps について

実は、Perl 版 YATT のテンプレートをあまり変更せずに使えるようにしたい、という意図があります。Perl 版のユーザーがせっかく覚えてくれたものを変えることは、
良くないことだという考えが有るからです。
また `BODY` という名前は元は `body` でしたが、これが form で用いる body という名前と衝突しがちであることから yatt-js ではデフォルトを `BODY` に変えた、という事情があります（設定で変更可能なので Perl 版と互換に出来る）
